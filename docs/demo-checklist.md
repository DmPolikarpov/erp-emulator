# Чек-лист показа (M8)

Перед показом демо проходят две разные проверки: **автоматическая** (её видно в
терминале) и **ручная** (её видит зритель). Этот файл — вторая, плюс список
команд для первой. Раздел 8
[roadmap](dairy-plant-roadmap.md#8-как-проверять) задаёт сценарии; здесь они
превращены в пункты с ожидаемым результатом и местом для отметки.

Журнал прогона — в конце файла. Скриншоты — `docs/demo-artifacts/`
(см. [README](demo-artifacts/README.md)); видео ссылкой, не файлом.

## 0. Окружение

| Проверка | Команда | Ожидаемо |
| --- | --- | --- |
| Кластер поднят | `kubectl get pods` | движок, шлюз, Postgres, NATS — `Running` |
| Шлюз доступен локально | `wip\port-forward.cmd` (или `kubectl port-forward svc/http-cluster-service 8080:8080`) | в `port-forward.log` — `Forwarding from 127.0.0.1:8080`; `curl http://localhost:8080/api/v1/orders` отвечает 200 |
| Проброс жив после пересборки | повторить `wip\port-forward.cmd` после `rollout restart`, затем F5 в кабинете | в журнале кабинета нет «API заказов вернул ошибку (500)»: 500 с пустым телом — это CRA-прокси без живого проброса, а не отказ движка |
| Кабинет запущен | `npm start` в `erp-simulator` | `http://localhost:3000` открывается без оверлея ошибки |
| `.env` на месте | `type .env` | `REACT_APP_GATEWAY_URL`, `REACT_APP_WS_URL`, `REACT_APP_METRICS_API_URL` |
| Чистая БД (для показа «с нуля») | `wip/db-wipe.sql` через `kubectl exec … psql` | таблицы `process_instances`, `tokens`, `orders` пусты |
| Сброс заказов (перед новым показом) | в кабинете: «Очистить все заказы» в баре «Внутренние заказы» или в панели «Приём заказов» (`DELETE /api/v1/orders`) | список пуст — «Заказов пока нет.»; экземпляры процессов и журнал остаются, поэтому заказ можно играть заново |

## 1. Автоматические проверки

```bash
cd erp-simulator
npm run test:ci                 # Jest: схема, кабинет, метрики
npm run sdk:verify              # артефакты SDK совпадают с исходниками
npm run build:verify            # production-сборка + маркеры демо в бандле
cd ..
tests/run-live-e2e.sh           # живые API: orders, roles, metrics, ws-filter
node wip/live-metrics-check.cjs # живой ответ /api/v1/metrics через CRA-прокси
```

`npm run build:check` отдельно проверяет, что в бандле есть три процесса демо,
роли кабинетов, кнопки участников, панель приёма заказов M5, клиент метрик M7, и
что сборка не старше исходников
([`scripts/check-bundle.mjs`](../scripts/check-bundle.mjs)). Сборка идёт дольше
30 с (терминал обрывает команды), поэтому её запускают в фоне обёрткой
`wip\build-cabinet.cmd` через `wip\run-bg.ps1`: готовность — маркер `BUILD_EXIT=`
в `build-cabinet.log`.

## 2. Сценарий A — контур завода (M0)

Вход: «Менеджер по продажам» → проект «Молочный завод: заказ → производство →
отгрузка» → панель «Приём заказов» → «Задеплоить схему приёма». Кнопка
«Задеплоить BPMN в Оркестратор» нарисована только роли `EXECUTIVE`
(«Руководитель завода»): это второй путь для показа, заказ она не создаёт.

| # | Шаг | Ожидаемо | ✓ |
| --- | --- | --- | --- |
| A1 | Заказ приходит от клиента (сценарий B): «Менеджер по продажам» видит его в панели «Приём заказов» («Обновить список заказов»); кнопки старта у завода нет — `Start_Dairy` ждёт сообщение `ClientOrder` | активный шаг `Task_ReceiveOrder` («Принять заказ клиента») | |
| A2 | «Зарегистрировать заказ в 1С:УТ» | шаг `Task_ProcessOrder` | |
| A3 | «Проверить лимит и подтвердить сроки» | развилка остатков ГП (`Task_CheckStock`): «ГП хватает — отгрузить со склада» / «ГП не хватает — закупить сырьё» | |
| A4 | «ГП не хватает — закупить сырьё» → вход «Менеджер по закупкам» → «Рассчитать потребность и создать заказ» | активный шаг у закупок (`Task_ApprovePO`) | |
| A5 | «Согласовать в пределах лимита» → «Отправить заказ поставщику» | в журнале движка — старт процесса поставщика | |
| A6 | Вход «Менеджер по продажам сырья» → «Принять заказ на сырьё» → «Погрузить и передать перевозчику» | событие `milkShipped`, у завода оживает приёмка | |
| A7 | «Приёмка и лаборатория»: «Проверить ТТН, пломбы и температуру» → «Взвесить и отобрать пробы по ГОСТ» → «ГОСТ ОК — оприходовать партию» → «Присвоить номер партии в 1С:ERP» | шаги идут по дорожкам пула (`Task_ReceiveMilk` → `Task_StoreMilk`) | |
| A8 | Производство: очистка → нормализация → гомогенизация → пастеризация → ферментация → контроль ТУ → розлив | после каждого нажатия подсвечен следующий узел | |
| A9 | «Скомплектовать, оформить УПД и ТТН» | узел отгрузки, процесс завода ждёт клиента/конец | |
